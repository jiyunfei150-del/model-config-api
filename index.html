模型配置接口手册

模型配置页上的「模式 / 框架与过程模型 / 结果与分析模型」整份存成一份配置；能接哪些厂商由后端登记；保存后下一条问数就按新配置调模型，不用重启服务。

前缀 /model-config/api/v1 格式 JSON 更新 2026-09-29
●后端状态：开发完成，尚未部署到预发。部署并打开接口后会通知联调；在此之前请按本文档先开发页面。

怎么运作

页面编辑→试校验→保存（整份）→下一条问数生效
  • 整份替换：每次保存都提交完整配置，JSON 里没有的 Key 即删除。
  • Key 存在后端：只在提交时传明文，之后任何接口只返回掩码。
  • 生效：保存后本服务下一条问数立即用新配置；正在跑的那一条用旧配置跑完；同机其它进程 5 秒内跟上。
  • 效果档：三个框架（cc / cx / react）各有低、中、高三档，前端传的效果档 low / medium / high 对应三档，auto 或不传走中档。
  • 所有模型默认不思考。

对接步骤

  1. 「接入厂商」下拉用 GET /providers 的结果，页面只选厂商、不填地址。
  2. 用户添加模型时，用 POST /providers/{id}/models 列出这把 Key 能用的模型供选择。
  3. 需要时用 POST /connectivity 测某个模型通不通。
  4. 点「校验」调 POST /config/validate，把 errors[].path 标到对应的表单项上。
  5. 点「保存」调 PUT /config，把整份配置推给我们。配置以前端为准，每次都推完整的一份。

前端上线时只需做一次：调 GET /config 取 initial（按服务器当前在用的模型算好的一份）作为页面初始值。之后平时不用调它，它只用于排查服务器上当前生效的是哪一份。

通用约定

项说明
鉴权与现有问数接口（/ask/stream）相同：调问数时怎么带 X-Api-Token，这里就怎么带，不需要额外处理。
操作人可选请求头 X-Operator: <用户标识>，记录谁保存的。
失败格式{"error": {"code", "message", "field_errors": [{"path","code","message"}], "current_revision"}}；path 直接指到你们提交的 JSON，如 /engines/cc/tiers/low。
状态码401 令牌不对 · 404 厂商不存在，或服务器没打开模型配置开关（整组接口不存在）· 409 版本冲突 · 422 字段错误或 Key 无效 · 429 厂商限流 · 502 厂商请求失败

接入厂商

GET/providers

后端已适配的厂商，「接入厂商」下拉的唯一来源。

响应
{
  "providers": [
    {"id": "anthropic", "name": "Anthropic 官方", "protocols": ["anthropic"],
     "business_data": false,
     "default_key": {"env": "ANTHROPIC_OFFICIAL_KEY", "configured": true},
     "static_models": []},
    {"id": "openapi", "name": "OpenAPI 内网网关", "protocols": ["openai"],
     "business_data": true, "...": "..."}
  ],
  "revision": "prv_…"
}
字段说明
id厂商标识，配置里的 provider 填它。目前有 gateway（AI 网关）、openapi（OpenAPI 内网网关）、anthropic、glm_coding、deepseek、minimax。
business_data能否处理真实业务数据。只有 true 的厂商能当「结果与分析模型」；目前只有 OpenAPI 内网网关。也可能是模型名清单，表示只有这些模型可以。
default_key.configured服务器上已有这家的默认 Key，页面不给 Key 也能用。
static_models厂商没有列模型接口时后端登记的固定清单。

列可用模型

POST/providers/{provider_id}/models

列出某厂商某把 Key 能用的模型。请求体三选一。

请求
{"secret": "sk-…"}      // 新填的 Key
{"key_id": "k_glm"}     // 已保存的 Key
{}                      // 用服务器上这家的默认 Key
响应
{
  "provider_id": "anthropic",
  "source": "remote",
  "models": [
    {"id": "claude-opus-5-5", "name": "Opus 5.5"},
    {"id": "claude-fable-5-1", "name": "Fable 5.1"}
  ],
  "note": ""
}
source含义页面怎么做
remote厂商实时返回直接给用户选
static厂商没有列模型接口，给的是后端登记的清单给用户选，同时允许手填
manual两者都没有让用户手填模型名

Key 无效返回 422（AUTH_FAILED），限流 429，连不上或超时 502。

页面配置

GET/config

可选。平时不用调：前端上线时取一次 initial 作为初始值；之后只用于排查服务器上当前生效的配置。Key 只返回来源与掩码。

已保存过
{
  "config": { …与保存时同形状，keys[] 见下表… ,
              "revision": "cfg_…", "updated_at": "2026-09-29T10:00:00+00:00",
              "updated_by": "u_xxx" },
  "revision": "cfg_…"
}
还没保存过
{
  "config": null,
  "revision": "",
  "initial": { …按服务器当前在用的模型算出的同形状配置，keys 为空… },
  "initial_check": {"valid": true, "errors": []},
  "initial_notes": ["cx：本机缺该框架的运行依赖，初始值里先关掉"]
}

initial 里各档只写 provider 不写 key，表示沿用服务器上各厂商的默认 Key。用户核对后原样保存即可，保存前后模型调用不变。initial_notes 列出需要页面补齐的项。

读回的 keys[] 字段说明
secret_sourcepage=页面填的明文 · env=服务器环境变量 · provider_env=厂商默认 Key
masked_secret掩码（如 sk-****bbbb），只用于展示，不能再提交回来
env_name用的是哪个环境变量
available服务器现在能不能取到这把 Key

请求体（试校验与保存相同）

{
  "modes": {"deep": "cc", "quick": "react"},
  "keys": [
    {"id": "k_an",  "provider": "anthropic",  "name": "公共 Key", "secret": "sk-…"},
    {"id": "k_glm", "provider": "glm_coding", "name": "公共 Key", "secret": "sk-…"},
    {"id": "k_oa",  "provider": "openapi",    "name": "公共 Key", "secret": "sk-…"},
    {"id": "k_gw",  "provider": "gateway",    "name": "公共 Key", "secret_env": "AI_GATEWAY_KEY"}
  ],
  "engines": {
    "cc": {"enabled": true, "provider": "anthropic", "tiers": {
      "low":    {"key": "k_glm", "model": "glm-5.3", "name": "glm-5.3"},
      "medium": {"key": "k_an",  "model": "claude-opus-5-5", "name": "Opus · 官方主用"},
      "high":   {"key": "k_an",  "model": "claude-fable-5-1"}}},
    "codex": {"enabled": true, "provider": "gateway", "tiers": {"low": {…}, "medium": {…}, "high": {…}}},
    "react": {"enabled": true, "provider": "auto",    "tiers": {"low": {…}, "medium": {…}, "high": {…}}}
  },
  "conclusion": {
    "primary":  {"key": "k_oa", "model": "local/glm-5.3-flash"},
    "fallback": {"key": "k_oa", "model": "local/qwen38-flash-next"}
  }
}
字段说明
modes深度 / 快速模式各由哪个框架承接，值为 cc / codex / react。界面叫 cx 的框架写 codex。
keys[]id（字母数字开头，最长 64 位，长期不变）、provider（厂商标识）、name（显示名），加密钥给法之一，见下。
每档模型model=厂商那边的实际模型名（可从「列可用模型」选）；key=keys 里的 id；name=显示名，可选。不给 key 时写 provider，用该厂商的服务器默认 Key。
engines.*.provider页面的「接入厂商」选择，只做记录；实际调用按每档所选 Key 的厂商走。auto=按模型自动路由。
engines.*.enabled框架开关。开启的框架三档都必须选；模式不能指向关掉的框架。
conclusion结果主模型与兜底，三个框架共用。必须是能处理业务数据的厂商，且主备不能是同一个。

Key 三种给法

写法含义
"secret": "sk-…"明文。新建或更换 Key 时用。
"secret_env": "变量名"用服务器上的环境变量。
都不给沿用已保存的那份（同一 id 且厂商没变）。新 Key 必须给。不改 Key 时去掉 secret 字段即可，不要把掩码传回来。
POST/config/validate

试校验，不保存、不落 Key。valid=true 表示这份内容现在保存一定能过校验。

响应
{"valid": false,
 "errors": [
   {"path": "/conclusion/primary", "code": "DATA_POLICY_DENIED",
    "message": "AI 网关（主网关） 的 GLM-5.3-FLASH 未登记可处理真实业务数据，不能当结果模型"}
 ]}
PUT/config

整份保存（配置以前端为准，每次推完整的一份）。可选请求头 If-Match: "<revision>"：带了且与服务器当前版本不一致会返回 409；前端是配置正本时不用带。

响应
{"config": { … }, "revision": "cfg_…", "changed": true}

内容和当前完全一样时不会重复写入，返回 changed: false。

连通测试

POST/connectivity

发一条最小请求测模型通不通，不保存任何东西。密钥给法同「列可用模型」。

请求
{"provider": "glm_coding", "model": "glm-5.3", "secret": "sk-…", "purpose": "cc"}
响应
{"provider_id": "glm_coding", "model": "glm-5.3",
 "ok": true, "outcome": "ok", "http_status": 200,
 "latency_ms": 812, "protocol": "anthropic", "message": "HTTP 200"}
outcome含义
ok通了
auth_failedKey 无效
model_not_found模型名不对，或这家没有这个模型
rate_limited被限流，不代表 Key 无效
request_rejected请求被拒（常见于模型名或参数不被接受）
timeout / unreachable超时 / 连不上，是地址或网络问题，不代表 Key 无效
upstream_error厂商其它错误

purpose 选按谁的接口测：cc / codex / react / conclusion（缺省）。例如 cc 只能接 anthropic 协议，DeepSeek 测 cc 会返回 ENGINE_INCOMPATIBLE。

错误码

code含义页面提示建议
MASKED_VALUE把掩码当密钥提交不改 Key 就别传 secret
SECRET_UNAVAILABLE没给密钥，服务器也没有默认 Key请填写 Key
REQUIRED开启的框架缺档 / 主备缺一 / 模式没选标红对应项
UNKNOWN_PROVIDER厂商不在已适配清单里重新选厂商
DANGLING_REFERENCE引用了不存在的 Key重新选 Key
ENGINE_INCOMPATIBLE该框架用不了这家（协议不支持）换厂商或换框架
ENGINE_DISABLED模式指向了关掉的框架同一次保存里改掉模式映射
DATA_POLICY_DENIED该厂商不能处理业务数据，不能当结果模型结果模型改选内网模型
SAME_CALL_TARGET兜底和主模型是同一个换一个兜底模型
REVISION_CONFLICT别人先保存了重新读取后再改
AUTH_FAILED列模型时 Key 无效检查 Key

问数请求怎么用快速 / 深度

/ask/stream 请求体带 "interaction_mode": "deep" 或 "quick"，后端按页面配置的模式映射选框架；显式引擎路径（如 /ask/stream/cc）优先于模式映射。
